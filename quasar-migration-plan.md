# Quasar Migration Plan

## Objective

Migrate the remaining Quasar configuration from `oldflake` into the dendritic flake without changing its effective runtime behavior.

The target design must satisfy these constraints:

- Quasar selects one new `den.aspects.server` aspect instead of assembling server internals in the host module.
- Server services live under `modules/features/server/services/`.
- Every independently operated service or stack is its own aspect and is explicitly included by `den.aspects.server`.
- A service aspect owns its runtime definition, persistence, routes, ports, firewall rules, secrets, monitoring registration, and private sidecars.
- Persisted paths, identities, ports, routes, credentials, and service behavior remain compatible with the currently deployed Quasar generation.
- Structural improvements are allowed, but unrelated runtime changes are deferred until after parity is established.
- The implementation ends after local evaluation, checks, and builds. Deployment and live-host verification remain manual owner steps.

## Decisions From The Lens Debate

The Lowy and Hickey reviews converged on the following boundary:

- `server` owns host substrate and composition.
- A service aspect owns an operational capability.
- Private implementation processes stay inside the parent service aspect.
- Shared infrastructure with an independent lifecycle gets a separate aspect.

Examples:

- Keep Booklore and MariaDB in one aspect.
- Keep Paperless and Redis in one aspect.
- Keep TubeArchivist, Redis, and Elasticsearch in one aspect.
- Keep Radarr or Sonarr with its exporter.
- Keep AdGuard with its exporter.
- Keep Homepage with its Docker socket proxy.
- Keep Beszel with its agent.
- Keep Portainer with its agent.
- Keep PostgreSQL private to Home Assistant while Home Assistant is its only consumer.
- Give Mosquitto and InfluxDB separate aspects because they are independently operated infrastructure.
- Keep both qBittorrent instances in one aspect, using a small private instance helper.
- Keep Alloy as the cross-host monitoring client. Split the server daemons Grafana, Prometheus, and Loki into separate server service aspects.

Do not reproduce `oldflake/hosts/quasar/services/containers.nix` as a new aggregate module. Do not add a general service DSL during the parity migration.

## Known Parity Gaps

The current partial migration already differs from the old deployable configuration.

| Gap | Evidence | Required result |
| --- | --- | --- |
| Server identity is absent | `oldflake/modules/nixos/nas.nix`; the `data` user is commented in `modules/hosts/quasar/quasar.nix` | Restore `data:data`, UID/GID `911:911`, its shell, and conditional supplementary groups. |
| Portainer state moved | Old Quasar override uses `/pool/data/portainer`; current aspect uses Gabe's home | Preserve `/pool/data/portainer`. |
| Traefik's Quasar additions have not moved | `oldflake/hosts/quasar/services/traefik.nix` sets `/config/pods/traefik`, ports 80/443, TLS material, and `homeassistant-allow-iframe` | Migrate those additions into the existing network Traefik aspect's server provider. |
| Service secrets have not moved | The new Quasar SOPS file has only the already-migrated keys | Leave both SOPS files untouched and point not-yet-migrated service declarations at `oldflake/hosts/quasar/secrets.yaml`. |
| Docker network creation is race-prone | The old activation script exits when Docker is unavailable | Replace it with Docker-ordered oneshot systemd units generated by the container aspect from stack-owned network declarations. |
| Port values have multiple owners | Old `nas.ports`, `network.finalServices`, and monitoring constants overlap | Put each application port in its service aspect and contribute only shared route/scrape metadata. |
| A Home Assistant dependency disappeared | The custom `python-unifi-ap` package was removed and is not in current nixpkgs | Restore the package or explicitly retire the integration. Default to restoring it. |

## Aspect Contracts

### Server

`modules/features/server/server.nix` should:

- Define typed `host.settings.server` values for user, group, UID, GID, and persistent roots.
- Default Quasar-compatible roots to `/config/pods`, `/pool/data`, `/pool/downloads`, and `/pool/media`.
- Create the `data` user and group with IDs `911:911` and preserve the old conditional supplementary groups.
- Enable the container provider through `den.aspects.virtualisation._.containers`.
- Include `den.aspects.network` and the network server provider.
- Include the Traefik server provider from the existing network Traefik aspect.
- Include every service aspect explicitly by its unprefixed service name.
- Contain no application-specific runtime definitions.
- Disable password prompts for wheel only here, not in the Quasar host module.
- Leave timezone ownership in `base`; Quasar keeps the base default of `America/Edmonton`.
- Expose one legacy Quasar SOPS file path for not-yet-migrated service declarations without changing either encrypted file.

After this exists, `modules/hosts/quasar/quasar.nix` should include `den.aspects.server` and stop directly including `network._.server`, `monitoring._.server`, DNS, or individual services.

### Service

Each service aspect should own all configuration that changes with that service:

- Native NixOS service or OCI container definitions.
- Image, command, environment, environment files, ports, volumes, network mode, capabilities, devices, dependencies, and labels.
- Persistent data paths derived from `host.settings.server`.
- SOPS declarations with exact owner, group, mode, output path, and environment-file semantics. Until manually migrated, these explicitly use the server's legacy Quasar SOPS file path.
- Static Traefik route registration for native and host-network services, or Docker labels for bridged OCI services.
- Homepage metadata, either as Docker labels or as a contribution to the shared static Homepage list.
- Firewall openings that are not represented by an ordinary reverse-proxy route.
- Monitoring scrape targets owned by the service.
- Private sidecars and private Docker network setup.

### Shared Contracts

Keep shared contracts narrow:

- Keep `network.services` as the native/host-network reverse-proxy route registry.
- Remove hard-coded `cockpit` and `traefik` entries from `network.finalServices`; their aspects register their own ports.
- Add a typed monitoring scrape-target registry so service aspects contribute local targets and Alloy renders them. This replaces hard-coded AdGuard, Navidrome, UniPoller, and exportarr ports in `monitoring.nix`.
- Keep Docker labels for bridged containers. Static routes and Docker labels are distinct provider mechanisms and should not be forced behind a new abstraction.
- Add only stable volume and default PUID/PGID/TZ environment helpers to `lib/server`. Derive `TZ` from the base-owned system timezone.
- Keep Docker network options and systemd-unit generation in `den.aspects.virtualisation._.containers`. Stack aspects contribute the network names they own; the container provider owns the Docker-specific mechanics.
- Keep `den.aspects.traefik` in `modules/features/network/traefik.nix`. Add its Quasar-only data directory, TLS certificate, firewall, and `homeassistant-allow-iframe` configuration under `provides.server.nixos`, selected by `den.aspects.server`.
- Avoid enable options for every service. Composition through `server.includes` is the enablement mechanism.

## Implementation Sequence

### Phase 0: Freeze The Runtime Baseline

1. Identify the last deployable Quasar commit before the old configuration was moved under `oldflake`.
2. Evaluate that commit in a temporary worktree and capture normalized JSON projections of the Quasar configuration.
3. Inventory the current `oldflake/hosts/quasar/services/**` sources for configuration added after that commit.
4. Record intentional new-flake differences, including Quasar's current IP and FQDN.
5. Record the Cachix agent and Minecraft firewall ports `25565` and `24454` as intentional removals. Do not migrate them.

The parity manifest must cover:

- Users, groups, UID/GID, base-owned timezone, and persistent roots.
- Native service enablement and settings.
- OCI container names and complete definitions.
- Routes, labels, certificates, DNS behavior, and firewall ports.
- Secret key names and generated ownership/modes/paths, never secret values.
- Docker networks and service ordering.
- Home Assistant integrations, packages, custom components, Lovelace modules, and database dependencies.

Gate: no implementation starts until the baseline and intentional exceptions are written down.

### Phase 1: Add The Server Substrate

1. Add `lib/server/default.nix` with only stable path and default-container-environment helpers.
2. Export it from `lib/default.nix`.
3. Add `den.aspects.server` and typed server settings without selecting the aspect on Quasar yet.
4. Implement the `data:data` identity, Docker provider, and server-only sudo policy. Keep timezone configuration in `base` and accept `America/Edmonton`.
5. Add a server-level path that not-yet-migrated service secret declarations use to reference `oldflake/hosts/quasar/secrets.yaml` explicitly.
6. Add Docker network declaration and unit generation to the existing container provider rather than `lib.server`.
7. Add assertions for non-empty absolute roots, unique UID/GID, and required mounted roots where Nix assertions can catch mistakes safely.

Gate:

- Quasar still evaluates without selecting `server`.
- A test host selecting only `server` evaluates with UID/GID `911:911` and the exact old paths.
- `nix fmt` and `nix flake check --impure` pass.

### Phase 2: Correct Existing Aspect Boundaries

1. Move Cockpit and Portainer implementations into `server/services/` while retaining the aspect names `cockpit` and `portainer`.
2. Parameterize Portainer persistence so Quasar uses `/pool/data/portainer`.
3. Remove Cockpit and Portainer from generic `base`.
4. Explicitly include them from `workstation` as well as `server` if the parity baseline confirms Bastion and Voyager currently run them.
5. Keep `den.aspects.traefik` in `modules/features/network/traefik.nix`.
6. Add a Traefik server provider containing the old Quasar `dataDir`, TLS certificate/default store, ports 80/443, and `homeassistant-allow-iframe` middleware. Use `config.networking.fqdn` in place of old NAS-derived names.
7. Have `den.aspects.server` include that Traefik server provider; do not move or rename the network aspect.
8. Move CoreDNS into `server/services/coredns.nix`.
9. Keep Alloy and the generic monitoring options in `network/monitoring.nix`.
10. Move Grafana, Prometheus, and Loki server definitions into separate unprefixed service aspects.
11. Replace the existing `monitoring._.server` implementation with service-owned registrations and one shared monitoring topology contract.

Gate:

- Bastion and Voyager derivations retain intended Cockpit, Portainer, Traefik, Alloy, and Docker behavior.
- Quasar evaluation has no duplicate route or service definitions.
- Each moved aspect can be evaluated independently.

### Phase 3: Restore Ingress, DNS, And Platform Services

Implement these aspects first because most later services depend on them:

- Traefik's existing network aspect and its new server provider

- `coredns`

- `pocket-id`
- `ddclient`

- AdGuard's dedicated certificate, SANs, DNS ports, exporter, volumes, and TLS modes.
- CoreDNS forwarding to AdGuard over TLS and its internal wildcard zones.
- Homepage's static entries, settings YAML, environment file, and read-only Docker socket proxy.
- Existing CI agent names, repository URL, token paths, owners, and settings.

Gate:

- DNS, TLS, route, firewall, and persistent-path projections match the baseline.
- No route points at a port without an owning enabled service.

### Phase 6: Migrate Home Automation

Implement and validate this as the highest-risk dependency chain:

3. Preserve the complete Home Assistant component, custom component, Lovelace, URL, proxy, SMTP, sensor, shell command, and YAML include configuration.

6. Add `mosquitto` with the exact users, ACLs, password files, data directory, and port 1883 firewall behavior.

### Phase 7: Configure Legacy Secrets And Compose Server

1. Do not edit `oldflake/hosts/quasar/secrets.yaml` or `secrets/hosts/quasar/secrets.yaml`.
2. Keep already-migrated secret declarations pointed at their current SOPS files.
3. Point each not-yet-migrated service secret declaration at the server's legacy Quasar SOPS file path.
4. Preserve every old owner, group, mode, target path, and environment-file use.
5. Complete the explicit `den.aspects.server.includes` list using unprefixed service aspect names.
6. Select `den.aspects.server` from `modules/hosts/quasar/quasar.nix`.
7. Remove direct Quasar includes now owned by server, while retaining the network Traefik aspect and selecting its server provider through `server`.
8. Remove host-level Grafana secret pass-through after the Grafana aspect owns its declaration.
9. Build the complete Quasar closure without deploying it.

Gate:

- Neither encrypted YAML file changes.
- Every `config.sops.secrets.<name>` reference evaluates against either its existing migrated file or the explicit legacy Quasar file.
- Generated secret owner, group, mode, and path match the old service configuration.

### Phase 8: Build And Hand Off

Run local verification only:

```bash
nix fmt -- --check
nix flake check --impure --print-build-logs
nix eval --impure .#nixosConfigurations.quasar.config.system.build.toplevel.drvPath
nix build --impure --no-link --print-build-logs .#packages.x86_64-linux.quasar
```

Compare normalized old and new projections for:

- OCI names, images, commands, environment, environment files, ports, volumes, labels, networks, dependencies, and extra options.
- Native service enablement and settings.
- Route registry, Traefik static/dynamic config, Homepage entries, certificates, and firewall ports.
- Users/groups, UID/GID, timezone, persistent paths, and secret metadata.
- Docker network units and ordering.
- Monitoring topology and scrape targets.
- Home Assistant packages and integration configuration.

Do not run `deploy-rs`, `nixos-rebuild switch`, remote activation, container pulls, or live-host commands. Produce a handoff containing:

- The final build result.
- The normalized parity comparison and any intentional differences.
- Expected service/container additions and restarts.
- Persistent path and secret metadata checks.
- A manual owner checklist for DNS, ingress, storage, Home Assistant, media, monitoring, and backups after deployment.

### Phase 9: Remove Migrated Sources

After the complete local build passes:

1. Remove migrated Quasar `.nix` files under `oldflake/hosts/quasar/`, but preserve `oldflake/hosts/quasar/secrets.yaml` byte-for-byte.
2. Remove the old NAS module if no remaining oldflake host imports it.
3. Remove `lib/nas/` and stale helper exports.
4. Remove replaced base service files. Keep `modules/features/network/traefik.nix` in place.
5. Run the full CI command from `justfile`.
6. Re-run the Quasar build and verify the deploy target still evaluates.
7. Stop. The owner performs deployment and live verification separately.

## Risk Controls

| Risk | Control |
| --- | --- |
| A wrong persistence path starts a blank service | Compare every host path before activation and stop on any unexplained difference. |
| Floating OCI tags pull changed software during migration | Preserve tags for parity, record deployed digests, and handle digest pinning as a follow-up behavior change. The owner can pre-pull during manual deployment. |
| Legacy SOPS fallback reads the wrong file or changes metadata | Do not edit either encrypted file; explicitly select the legacy file only for unmigrated keys and compare generated secret metadata. |
| CoreDNS switches before AdGuard is healthy | Test AdGuard TLS and port 853 before making CoreDNS authoritative. |
| Current nixpkgs options differ from the old lock | Build every native service aspect incrementally and adapt only where the current option schema requires it. |
| Moving generic aspects changes Bastion or Voyager | Preserve intended behavior with explicit workstation includes and compare both derivations. |
| Docker `dependsOn` is mistaken for readiness | Preserve ordering only; do not claim health readiness without explicit probes. |
| A later deployment restarts many services at once | Document expected restarts and stateful risks in the handoff; leave deployment sequencing and rollback to the owner. |
| Home Assistant custom packages lag current Home Assistant | Build every package and include startup-log checks in the owner's post-deployment handoff. |

## Default Answers To Open Decisions

- Parity baseline: current remaining oldflake service sources plus the last deployable pre-migration Quasar configuration.
- Private sidecars: keep inside the parent operational service aspect.
- Monitoring: keep generic Alloy/client topology outside server; split Grafana, Prometheus, and Loki into server aspects.
- Timezone: keep it in `base`; `America/Edmonton` is accepted.
- Cachix agent and Minecraft ports: intentionally removed; do not migrate them.
- Aspect names: use unprefixed service names.
- Traefik: keep the aspect in `modules/features/network/`; migrate Quasar additions into its server provider.
- Secrets: do not edit either SOPS file; use the old Quasar file for not-yet-migrated service keys.
- Docker network units: keep their option and generation mechanics in the container aspect, with stack-owned declarations.
- OCI image pinning: do not change update semantics during migration; capture digests and decide separately.
- AdGuard certificate: preserve the dedicated certificate and SAN behavior until TLS parity is proven.
- Unused old secrets: do not migrate without a live reference.
- Suspicious old settings: preserve them unless they cannot evaluate; fix them in follow-up changes.
- Workstation admin services: preserve current intended behavior through explicit workstation includes rather than generic base includes.
- Deployment: never deploy or activate Quasar as part of implementation; hand the built result and checks to the owner.

## Completion Criteria

The migration is complete when:

- Quasar includes `den.aspects.server` and no server implementation details directly.
- Every operational service is an aspect under `modules/features/server/services/` and is included by `server`.
- Service aspect names are unprefixed.
- Traefik remains a network aspect, and its server provider contains the migrated Quasar data directory, TLS, firewall, and iframe middleware additions.
- The complete Quasar closure builds from the new flake.
- Normalized configuration and local build checks show no unexplained differences; live checks are listed for the owner.
- Stateful services use their existing data paths and identities.
- The implementation handoff documents the owner's DNS, ingress, monitoring, backups, media, download, and home automation checks.
- Neither encrypted SOPS file is modified, and unmigrated keys still resolve from the old Quasar file.
- Migrated Quasar Nix sources and obsolete NAS helpers are removed without deleting the legacy secret file or unrelated oldflake archives.
- No deployment or activation command has been run.
